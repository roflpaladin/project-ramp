# ADR 0001: Transactional email provider

- Status: Accepted
- Date: 2026-09-04
- Ticket: Sprint 11, Ticket 57 — "Transactional email deliverability"

## Context

The only transactional email this app sends today is the buyer's 4-digit
portal access code (`lib/email/send-access-code.ts`), used by the buyer-gate
resend flow, the seller-invite flow, and `POST /api/auth/send-token`. Through
Sprint 10 it sent via Google Workspace's SMTP relay (`smtp.gmail.com`) using
nodemailer.

Sprint 11's ACs (due ahead of the Nov 1 sellable date) require bounce and
delivery visibility for this send: knowing whether an invited buyer's access
code actually arrived, bounced, or was suppressed. Google Workspace's SMTP
relay gives none of this — Workspace has no delivery-event API or dashboard
for mail relayed through it; a bounce or spam-folder landing is invisible to
us. Nudge emails (a planned follow-up, not built in this ticket — see Lean
scope below) will make this worse: more sends, more surface for silent
failures we can't see.

## Options considered

**1. Stay on Google Workspace SMTP.** No code change, no new vendor. Rejected
— cannot produce delivery/bounce metrics; the hard AC is unmet regardless of
how the send code is written. Also carries an operational risk this ticket
doesn't fix: an app password stored as a plain env var, no dedicated
send-only identity separate from a human's mailbox.

**2. Resend.** Purpose-built transactional email API with a first-party
Node/TypeScript SDK (`resend`), a dashboard with per-email delivery status
(sent/delivered/bounced/complained/opened), a generous free tier (3,000
emails/month, 100/day) that comfortably covers current + projected
access-code volume, and the simplest SDK swap of the options considered —
`transport.sendMail({...})` → `resend.emails.send({...})` is close to a
like-for-like replacement, keeping this a lean, low-risk cutover.

**3. Postmark.** Comparable delivery-visibility feature set and a similarly
simple SDK. Acceptable substitute if Resend's onboarding or domain
verification proves to be a blocker later. Not chosen only because Resend's
free tier and SDK ergonomics were marginally better for this app's current
(low) volume — this is not a strong technical preference, and revisiting it
is cheap given both providers are swapped behind the same
`sendAccessCodeEmail()` contract.

## Decision

Use **Resend** (`resend` npm package) for all transactional email sent by
this app, starting with the access-code send. Nudge emails and any other
future transactional sends should use the same provider and the same
`lib/email/send-access-code.ts` / `lib/email/templates/*` pattern (provider
call isolated from template construction) rather than introducing a second
provider.

Delivery and bounce metrics are read from **Resend's dashboard** for now.
This ticket deliberately does not add a `email_events` table, a webhook
receiver, or any in-app metrics surface — that is real, but not lean, scope
and is a flagged follow-up (see Lean scope below).

## Lean scope (what this ticket does NOT do)

- No nudge-email implementation. Nudge emails don't exist yet in this
  codebase; wiring them to Resend is follow-up work once they're built, not
  part of this ticket.
- No `email_events` table, no Resend webhook receiver, no in-app
  delivery/bounce dashboard. The Resend dashboard is the source of truth for
  delivery metrics until in-app surfacing is prioritized.
- No new template engine (no react-email, no MJML). Templates stay plain
  TypeScript template-literal functions (`lib/email/templates/*.ts`),
  matching this codebase's existing preference for small, dependency-light
  modules over introducing a rendering framework for a single email.

## DNS records the founder must add

Resend needs domain authentication on `getbrava.tech` before it can send
from `noreply@getbrava.tech` without landing in spam or being rejected by
strict recipients. **The founder has not yet created the Resend account or
verified the domain**; this ticket builds against placeholder env vars
(`RESEND_API_KEY`, `RESEND_FROM`), matching the existing project pattern for
not-yet-provisioned vendor credentials (see T52/T53). The exact record
values are generated by Resend when the domain is added under **Domains** in
the dashboard — the entries below are the record *types*, not final values.

- **SPF (TXT, root `getbrava.tech`)** — **extend** the existing SPF record
  with an additional `include:` mechanism for Resend's sending domain; do
  **not** replace it. Google Workspace sends normal company mail (and this
  app's own outbound mail did, pre-T57) on `getbrava.tech`, so the existing
  `include:_spf.google.com` (or equivalent) must stay. A domain can have only
  one SPF TXT record — merge, don't add a second.
- **DKIM (TXT, on Resend's selector subdomain)** — a `TXT` record at the
  selector hostname Resend's dashboard generates (typically
  `resend._domainkey.getbrava.tech` or similar — Resend shows the exact
  name). Additive; doesn't touch Google's own DKIM selector.
- **DMARC (TXT, `_dmarc.getbrava.tech`)** — if one doesn't already exist,
  add it starting at `p=none` (monitor-only) so a misconfigured SPF/DKIM
  alignment doesn't start silently dropping or spam-foldering existing
  Google Workspace mail on day one. Tighten to `p=quarantine`/`p=reject`
  only after confirming both Google Workspace and Resend mail align cleanly
  — that's an operational follow-up, not part of this ticket.
- **Bounce/return-path (CNAME), if Resend's dashboard requests one** —
  some Resend setups ask for a subdomain CNAME (e.g. for a custom
  `MAIL FROM`/return-path domain) to improve deliverability further. Add it
  only if the dashboard's domain-verification screen asks for it; skip
  otherwise.

All of the above are **additive** — verify in the Resend dashboard ("Domain
verified") before flipping `RESEND_API_KEY`/`RESEND_FROM` from placeholder to
real in any environment, per this repo's dev-then-prod rollout convention
(`docs/environments.md`).

## Rollback path

`sendAccessCodeEmail()`'s public contract (`{ to, code, portalUrl? }` in,
`{ ok: boolean }` out) is provider-agnostic by construction — every caller
imports the function, never a provider SDK directly. Reverting to SMTP (or
switching to Postmark) means re-implementing only the inside of
`lib/email/send-access-code.ts` against the old/new provider's SDK, unchanged
callers, unchanged `lib/email/templates/access-code.ts`. No data migration is
needed either direction since this ticket adds no new tables. If Resend's
sending is broken in production, the immediate mitigation is `{ ok: false }`
already fails soft everywhere it's called (token creation still succeeds;
the caller surfaces a "resend" affordance) — there is no send path this
ticket makes a hard dependency for any user-facing flow to complete.
